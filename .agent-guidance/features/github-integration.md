# GitHub Integration

GitHub remains the primary fully managed source-control integration. The deployment owns one shared GitHub App configuration, one or more GitHub App installations, and the repositories synced from those installations. Runtime git operations use GitHub App installation tokens; user OAuth mappings exist only for attribution and user-driven GitHub context. GitLab, Gitea, and Azure DevOps remain deployment-token backed for repository access. GitLab, Gitea, and Azure DevOps also have optional personal account-linking paths for comment attribution and gating; Azure DevOps account linking uses Microsoft Entra OAuth rather than legacy Azure DevOps OAuth.

The runtime carries a provider-neutral source-control discriminator on task payloads: `sourceControlProvider` defaults to `github` and may be set to `gitlab`, `gitea`, or `ado`. The provider boundary lives in [`packages/types/src/source-control.ts`](../../packages/types/src/source-control.ts), repository persistence, the SDK repository router, worker bootstrap token setup, provider-neutral PR/MR creation, and PR/MR review workflows. GitLab support starts as deployment-token support rather than a GitLab App: repository sync reads projects with `GITLAB_TOKEN` (validated against `/user` on save), persists `repositories.source_control_provider = 'gitlab'`, sync auto-creates merge-request webhooks on synced projects (generating and persisting `GITLAB_WEBHOOK_SECRET` when absent), GitLab-backed manual or environment launches clone from `gitlab.com`, GitLab merge-request webhooks can enqueue review automation, and the Roomote MCP source-control tool can create or refresh GitLab MRs. Gitea support follows the same deployment-token model: repository sync reads from `<GITEA_BASE_URL>/api/v1/user/repos` with `GITEA_TOKEN` (validated against `/user` on save), persists `repositories.source_control_provider = 'gitea'`, sync auto-creates pull-request webhooks on synced repositories (generating and persisting `GITEA_WEBHOOK_SECRET` when absent), Gitea-backed launches clone from the synced repository row's `cloneUrl`, Gitea pull-request webhooks can enqueue review automation and explicit `@roomote` follow-ups, and the Roomote MCP source-control tool can create or refresh Gitea PRs. Azure DevOps support is deployment-token-backed repository sync, checkout, service-hook setup, and PR creation: repository sync reads from `https://dev.azure.com/<organization>/_apis/git/repositories` with `ADO_TOKEN`, persists `repositories.source_control_provider = 'ado'`, sync auto-creates pull-request service hooks on synced repositories (generating and persisting `ADO_WEBHOOK_SECRET` when absent), ADO-backed launches clone from the synced repository row's `cloneUrl`, ADO pull request webhooks can enqueue review automation and explicit `@roomote` follow-ups, and the Roomote MCP source-control tool can create or refresh Azure DevOps PRs.

## Installation And Repository Sync

Source-control provider setup is folded into the same in-app, env-overridable model used by `/setup` for communications and inference. The `/setup` flow exposes three steps that replace the old hard-coded `github` step: `source-control-provider` (chooser), `source-control-config` (GitHub App manifest creation by default, or a per-provider/manual field form), and `source-control-connect` (GitHub App install redirect, or token-backed repository sync). Setup status is resolved by `buildSetupSourceControlStatus` in `@roomote/types` (`packages/types/src/setup-source-control-config.ts`), which mirrors the comms/inference model: process env takes precedence over encrypted deployment `environment_variables`, a provider is `configSatisfied` when all required fields are satisfied by either source, and a provider only counts as setup-complete (`setupSatisfied`) when it is also `connected` (active GitHub installation repositories, or at least one synced token-backed repository row). The `SetupNewState.sourceControlProvider` field persists the chosen provider.

GitHub fields: `NEXT_PUBLIC_GITHUB_APP_SLUG`, `GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY`, `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `GITHUB_WEBHOOK_SECRET`. GitHub setup defaults to `github.startCreateAppManifest`, which builds a server-side GitHub App manifest, posts it to GitHub, exchanges the callback `code` through `github.finishCreateAppManifest`, and saves the generated fields into encrypted deployment `environment_variables`; "Enter values manually" remains the fallback for existing GitHub Apps and production env management. Because the created app is private (`public: false`), it can only be installed on the account that owns it, so the manifest step exposes an optional GitHub organization input: when provided, the manifest POST targets `https://github.com/organizations/{org}/settings/apps/new` so the app is owned by (and installable on) that organization instead of the admin's personal account. The manifest webhook URL must be publicly reachable, so localhost `TRPC_URL` values fall back to `ROOMOTE_APP_URL` for manifest creation, and the manifest omits `installation` from `default_events` because GitHub rejects that event in app manifests. GitLab fields: required `GITLAB_TOKEN`, optional `GITLAB_CLIENT_ID` / `GITLAB_CLIENT_SECRET` / `GITLAB_WEBHOOK_SIGNING_TOKEN` / `GITLAB_WEBHOOK_SECRET`. Gitea fields: required `GITEA_BASE_URL` / `GITEA_TOKEN`, optional `GITEA_USERNAME` / `GITEA_CLIENT_ID` / `GITEA_CLIENT_SECRET` / `GITEA_WEBHOOK_SECRET`; the client id and secret are Gitea OAuth2 application credentials for personal linked accounts. Azure DevOps fields: required `ADO_ORGANIZATION` / `ADO_TOKEN`, optional `ADO_BASE_URL` / `ADO_USERNAME` / `ADO_CLIENT_ID` / `ADO_CLIENT_SECRET` / `ADO_TENANT_ID` / `ADO_WEBHOOK_SECRET`; the client id and secret are Microsoft Entra app credentials for personal linked accounts, not legacy Azure DevOps OAuth credentials. Saved secrets are never decrypted back to the browser; the UI shows a configured mask and lets admins replace values. tRPC mutations: `setupNew.saveSourceControlProviderChoice`, `setupNew.saveSourceControlConfig`, and the reusable `sourceControl.saveConfig` (Settings) all write into encrypted deployment `environment_variables` via `upsertDeploymentEnvironmentVariables`. The `sourceControl.configStatus` query returns the per-field saved/runtime status for the Settings form.

1. The user creates a GitHub App from `/setup` through GitHub's manifest flow, or manually provides existing GitHub App env vars.
2. Roomote exchanges the manifest callback code and saves the returned app id, slug, client id/secret, webhook secret, and private key into encrypted deployment env vars.
3. The user starts GitHub App installation from the returned install URL, the `/setup` source-control-connect step, or Settings.
4. The web app creates a pending installation record so the callback/webhook can match the installation.
5. GitHub delivers installation webhooks to `/api/webhooks/github`.
6. The API syncs the installation into `github_installations`.
7. Repository access is synced into `repositories`.
8. Environment setup and task routing use those repository rows.

The GitHub App setup URL must redirect back to `/github/callback`, and GitHub App settings should enable redirect-on-update so repository additions/removals return users to the app.

GitLab repository sync is token-backed. A deployment-level `GITLAB_TOKEN` can come from process env or encrypted environment variables; saving it through `/setup` or Settings validates it against the GitLab `/user` API and blocks definitive auth failures. The Source Control section under Settings > Environments exposes an admin GitLab sync action backed by the web tRPC `sourceControl.syncRepositories` command with `provider: 'gitlab'`. That command lists membership projects from the GitLab `/projects` API and upserts them into `repositories` with `installationId = null`, `githubRepoId = null`, and `externalRepoId = <project id>`. Missing previously active GitLab repositories are marked inactive. After the upserts, the command ensures a merge-request webhook on each synced project (URL resolved like the GitHub manifest webhook URL, skipped when only loopback URLs are configured), generating and persisting `GITLAB_WEBHOOK_SECRET` as an encrypted deployment env var when none exists, and returns a per-project webhook summary alongside the sync result. When admins also provide optional `GITLAB_CLIENT_ID` and `GITLAB_CLIENT_SECRET`, Better Auth exposes a GitLab row in Settings > Linked Accounts so users can authorize personal MR comment follow-up. Use [GitLab Connection Setup](./gitlab-connection-setup.md) for the current operator-facing setup path.

Gitea repository sync is token-backed and instance-specific. A deployment-level `GITEA_BASE_URL` and `GITEA_TOKEN` can come from process env or encrypted environment variables, with optional `GITEA_USERNAME` for Git-over-HTTPS credentials. Saving a new token through `/setup` or Settings validates it against the configured Gitea `/user` API and blocks definitive auth failures. The Source Control section under Settings > Environments exposes an admin Gitea sync action backed by the web tRPC `sourceControl.syncRepositories` command with `provider: 'gitea'`. That command lists repositories from Gitea's `/user/repos` API and upserts them into `repositories` with `installationId = null`, `githubRepoId = null`, and `externalRepoId = <repository id>`. Missing previously active Gitea repositories are marked inactive. After the upserts, the command ensures a pull-request webhook on each synced repository (URL resolved like the GitHub manifest webhook URL, skipped when only loopback URLs are configured), generating and persisting `GITEA_WEBHOOK_SECRET` as an encrypted deployment env var when none exists, and returns a per-repository webhook summary alongside the sync result. There is no Gitea App installation flow, but admins can optionally add `GITEA_CLIENT_ID` / `GITEA_CLIENT_SECRET` so users can link a personal Gitea account in Settings > Linked Accounts; explicit `@roomote` PR comment follow-ups fail closed for unlinked commenters instead of borrowing the repository sync owner's identity. Use [Gitea Connection Setup](./gitea-connection-setup.md) for the current operator-facing setup path.

Azure DevOps repository sync is token-backed and organization-specific. A deployment-level `ADO_ORGANIZATION` and `ADO_TOKEN` can come from process env or encrypted environment variables, with optional `ADO_BASE_URL` and `ADO_USERNAME` for non-default hosts or Git-over-HTTPS usernames. The Source Control section under Settings > Environments exposes an admin Azure DevOps sync action backed by the web tRPC `sourceControl.syncRepositories` command with `provider: 'ado'`. That command lists repositories from Azure DevOps' `/_apis/git/repositories` API and upserts them into `repositories` with `installationId = null`, `githubRepoId = null`, and `externalRepoId = <repository UUID>`. Missing previously active Azure DevOps repositories are marked inactive. After the upserts, the command ensures pull-request service hooks on synced repositories (URL resolved like the GitHub manifest webhook URL, skipped when only loopback URLs are configured), generating and persisting `ADO_WEBHOOK_SECRET` as an encrypted deployment env var when none exists, and returns a per-repository service-hook summary alongside the sync result. When admins also provide optional `ADO_CLIENT_ID` and `ADO_CLIENT_SECRET` for a Microsoft Entra app with Azure DevOps delegated permissions, Better Auth exposes an Azure DevOps row in Settings > Linked Accounts so users can authorize personal PR comment follow-up. Use [Azure DevOps Connection Setup](./ado-connection-setup.md) for the current operator-facing setup path.

## Runtime Auth

- Git clones and GitHub API mutations use a GitHub App installation token.
- GitHub App token creation resolves `GITHUB_APP_ID` and `GITHUB_APP_PRIVATE_KEY` through the deployment env resolver: process env values win, and encrypted `environment_variables` rows created by `/setup` or Settings are the fallback. A manifest-created app therefore does not require copying those fields into `.env` before tasks can start.
- Worker bootstrap asks for a provider-neutral source-control token. GitHub resolves to `GH_TOKEN` from the GitHub App installation token path; GitLab resolves to repo-scoped credentials minted from `GITLAB_TOKEN`, falling back to deployment-token credentials through the worker-local git proxy when the namespace cannot mint project access tokens (gitlab.com Free-tier groups); Gitea resolves to host/repository-scoped credentials from `GITEA_TOKEN`; Azure DevOps resolves to host/clone-path-scoped credentials from `ADO_TOKEN`.
- Long-lived harness processes do not inherit fixed source-control token env vars. The worker writes provider token files under `~/.roomote/`, exposes them through sourced token env scripts, and registers a file-backed git credential helper for GitHub plus GitLab's short-lived repo-scoped credentials. Gitea and Azure DevOps instead use a worker-local HTTPS proxy plus `git config url.<proxy>.insteadOf` rewrites so git keeps repository-scoped access without a task-readable copy of the deployment PAT. At job startup, env injection removes token files for providers absent from the current job so reused or resumed homes cannot re-export stale cross-provider credentials.
- Provider-neutral PR/MR creation and refresh are available through the built-in Roomote MCP `manage_source_control` tool rather than shelling out to provider-specific CLIs. The worker sends branch/title/body metadata to `POST /api/mcp/tasks/:taskId/source_control`; the API verifies that the cloud job token belongs to the requested task, checks the repository against the job scope, resolves the active synced repository row, and calls the provider API with server-side credentials. GitHub uses the repository's GitHub App installation token; GitLab, Gitea, and Azure DevOps use the deployment token sources already used for sync/runtime credentials.
- Multi-repository environments must resolve to one GitHub App installation for a single worker token.
- GitLab, Gitea, and Azure DevOps all-repositories workspaces are provider-filtered through synced repository rows. GitLab jobs require explicit repository scope so Roomote can mint repo-scoped project tokens; Gitea and Azure DevOps jobs can resolve all active synced provider rows and write exact host/repository credentials for each clone.
- `github_user_mappings` can identify a human actor for attribution, PR assignment, and "opened on behalf of" copy, but it must not be used for privileged runtime git operations.
- Better Auth `auth_accounts` rows with `provider_id = 'gitlab'`, `provider_id = 'gitea'`, or `provider_id = 'ado'` identify linked GitLab, Gitea, and Azure DevOps users for comment authorization and attribution; ADO rows are minted through Microsoft Entra and store the Azure DevOps `connectionData.authenticatedUser.id`, while Gitea rows store the stringified numeric Gitea user id from the instance's built-in OAuth2 provider. Explicit Gitea PR comment follow-ups are blocked unless a linked Gitea user can be resolved. Like GitHub user mappings, these identity links are signals only and do not replace deployment-token runtime credentials.
- Authorship and PR-owner rules are deployment-level behavior. Do not add new Roomote workspace or membership joins for authorship policy.

## Webhooks And Automations

| Event or source                                       | Main handler                 | Behavior                                                                                                                                                                                           |
| ----------------------------------------------------- | ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `installation.created` / update events                | GitHub install handlers      | Sync installations and repositories.                                                                                                                                                               |
| `pull_request.opened`, `reopened`, `ready_for_review` | `handlePrOpen`               | Enqueue initial review when Review Code is enabled.                                                                                                                                                |
| `pull_request.synchronize`                            | `handlePrSynchronize`        | Enqueue delta review when a previous review SHA exists.                                                                                                                                            |
| `pull_request_review.submitted`                       | `handlePrComment`            | Handles explicit `@roomote` PR review follow-ups; non-mention reviews schedule an idle-gated, notification-only message to the owning task's originating conversation (Slack, Teams, or Telegram). |
| `pull_request.closed`                                 | merge handler                | Updates PR facts and sends Slack merge notifications when configured.                                                                                                                              |
| `push` / scheduled conflict scan                      | conflict handlers            | Can enqueue conflict-resolution tasks when the deployment automation is enabled.                                                                                                                   |
| `workflow_run.completed`                              | `handleWorkflowRunCompleted` | Can enqueue CI-failure triage when the deployment automation is enabled.                                                                                                                           |

GitHub automations are stored in `background_automations` and route Slack destinations through `background_automation_targets`. Review Code reads the `review_code` automation settings for author scope: by default automatic reviews only run for Roomote-authored PRs, and the `reviewAllPullRequestAuthors` setting allows automatic reviews for PRs opened by other authors.

GitLab merge-request webhooks are handled at `/api/webhooks/gitlab`. Roomote accepts GitLab's signed webhook headers (`webhook-id`, `webhook-timestamp`, `webhook-signature`) when `GITLAB_WEBHOOK_SIGNING_TOKEN` is configured, and falls back to `X-Gitlab-Token` with `GITLAB_WEBHOOK_SECRET`. Both secrets resolve through the deployment env resolver (process env first, encrypted `environment_variables` rows as fallback), so secrets saved by `/setup`, Settings, or webhook auto-setup verify without also living in the process environment. Merge-request `open` and `reopen` enqueue the initial review workflow, `update` with `oldrev` enqueues delta review, and `close` / `merge` update linked PR/MR task status. Merged MRs on active synced GitLab repositories also notify linked Slack and Teams threads through the same `notifySlackPrMerge` / `notifyTeamsPrMerge` path GitHub uses (the GitHub-installation gate is skipped; the GitLab handler verifies the synced repository row instead). GitLab MR review payloads set the shared checkout `branch` and `sha` fields from `source_branch` and `last_commit.id`, in addition to the review-prompt metadata fields. GitLab MR review workflows intentionally avoid GitHub-only API calls and CLI instructions.

Gitea pull-request webhooks are handled at `/api/webhooks/gitea`. Roomote verifies the raw request body with Gitea's HMAC-SHA256 signature headers (`X-Gitea-Signature` or the compatible `X-Hub-Signature-256`) and `GITEA_WEBHOOK_SECRET`, which resolves through the deployment env resolver. Pull-request `opened` and `reopened` actions enqueue the initial review workflow, `synchronized` / pull-request sync events enqueue delta review, and `closed` events update linked PR status. Merged PRs on active synced Gitea repositories notify linked Slack and Teams threads through the same merge-notification path GitHub uses, with repository lookup gated by active `gitea` rows instead of GitHub installations. Gitea `@roomote` pull-request comments still bypass the automatic author allowlist because the mention is explicit, but they now require a linked Gitea commenter identity before Roomote will steer an existing task or enqueue a new review. Linked commenters get follow-ups attributed to their Roomote user; unlinked commenters get a link-your-account reply pointing at Settings > Linked Accounts instead of the follow-up running as the repository sync owner. Gitea PR review workflows intentionally avoid GitHub-only API calls and CLI instructions.

Azure DevOps webhooks are handled at `/api/webhooks/ado`. Roomote validates ADO deliveries with either the configured `x-roomote-webhook-secret` custom header or the Basic-auth password stored in `ADO_WEBHOOK_SECRET`, which resolves through the deployment env resolver. Pull-request created events enqueue initial review, source-branch update events enqueue delta review, status updates close or merge linked PR tasks, and comment events containing `@roomote` route into reusable PR owner tasks or enqueue a new review task. Explicit ADO comment mentions bypass the PR-author policy but require a Better Auth `auth_accounts` row with `provider_id = 'ado'` whose `account_id` matches the comment author's stable Azure DevOps identity id resolved during linked-account auth from `connectionData.authenticatedUser.id`. When the commenter is not linked, Roomote replies on the PR thread with a link-account instruction instead of starting work. ADO PR review workflows intentionally avoid GitHub-only API calls and CLI instructions.

## Data Model

Current GitHub-facing tables are deployment-wide unless they explicitly reference a user or task:

- `github_installations`
- `github_user_mappings`
- `github_pending_installations`
- `repositories`
- `github_pull_request_facts`
- `task_pull_requests`
- `background_automations`
- `background_automation_targets`

`repositories` is now provider-tagged. GitHub rows keep `installationId` and `githubRepoId`; GitLab rows use `externalRepoId` for the project ID and do not have a GitHub installation; Gitea rows use `externalRepoId` for the repository ID and clone from their synced `cloneUrl`; Azure DevOps rows use `externalRepoId` for the repository UUID, display `fullName` as `<organization>/<project>/<repository>`, and clone from their synced `cloneUrl`.

## Local Setup Notes

Roomote local development uses `ROOMOTE_PUBLIC_URL` as the stable public
base URL for GitHub callbacks and webhooks. Configure one GitHub App to use that
domain for callbacks and webhooks.
