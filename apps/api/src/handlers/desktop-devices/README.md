# Desktop device broker

This module is the server half of the development contract in `roomote-desktop/docs/development-broker-protocol.md`.

## Security model

- The desktop opens the WebSocket outbound; Roomote exposes no unauthenticated desktop-control endpoint.
- Upgrade authentication accepts only a valid Roomote MCP OAuth access token with the canonical `/mcp` audience and `mcp:roomote` scope.
- The token owner, active user record, active deployment, owner-bound device row, and revocation state are revalidated before every request and again before a response is returned.
- Device UUIDs are stable identifiers generated by the desktop, not credentials. A UUID already owned by another user is rejected.
- Remote `arm` does not exist. `type` and `submit` still require a local exact-target grant and `allowInput: true`.
- The broker forwards only the shared strict action schema, allows one in-flight request per device, bounds frame sizes and timeouts, and never audits payloads, typed text, images, bearer tokens, or error messages.
- Disconnect, protocol failure, timeout, shutdown, and revoke close the socket; the desktop client converts closure into local input stop state.

## Deployment boundary

Active sockets are intentionally process-local for this milestone. The database remains authoritative for ownership and revocation. In a multi-API-replica deployment, an MCP request that lands on a different replica fails closed instead of being routed to the wrong process. `lastInstanceId` lets callers distinguish that state. A Redis-backed relay and cross-instance revoke notification are required before multi-replica production rollout.

The implementation is fixture-tested but has not been deployed or exercised with production OAuth pairing. No release, migration application, or package publication is part of this change.
