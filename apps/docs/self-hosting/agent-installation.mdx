---
title: Automated self-hosting contract
description: A deterministic, safety-conscious contract for an agent installing Roomote.
---

This page is the installation contract for an agent asked to follow the
[self-hosting guide](/self-hosting). It complements the human-facing guide; it
does not replace the installer or authorize an agent to make privileged or
external-account changes without approval.

<Warning>
  Never ask the user to paste provider credentials, setup tokens, backup
  passphrases, or private keys into chat. Use Roomote's browser setup, the
  provider's own authorization page, or a protected secret store.
</Warning>

## Required outcome

Complete the installation only when all of these are true:

- Roomote runs on a supported Linux host and its systemd unit is enabled for
  reboot persistence.
- The final, stable public HTTPS origin reaches Roomote.
- The first admin completed the token-protected browser setup.
- Source control, inference, and a sandbox provider are configured.
- A real task can clone a repository, run a command, and return its result.
- Artifact upload works, and a live preview works when preview ports are
  configured.
- The operator has the status, logs, backup, restore, upgrade, and rollback
  commands and knows where encrypted backups are stored.

Services being merely `running` is not a completed installation.

## Safety and confirmation contract

Perform read-only detection without asking. Before changing anything, summarize
the detected platform, chosen topology, public-ingress plan, exact installer
command, and expected privileged changes.

Ask for confirmation immediately before any of these boundaries:

- installing or removing host software, using `sudo`, changing `systemd`, or
  writing under `/opt` or `/usr/local/bin`
- creating, resizing, deleting, or changing networking for a virtual machine
- changing a host, router, or cloud firewall, opening ports, or configuring
  port forwarding
- creating or changing DNS records, a Cloudflare Tunnel, or another externally
  billed or account-owned resource
- creating or installing a source-control, sign-in, or communications-provider
  app, granting repository/workspace access, or completing OAuth
- replacing an existing Roomote domain, TLS mode, preview layout, or operator
  override
- running `roomote restore`, deleting volumes, destroying infrastructure, or
  any other operation that can replace or delete data
- using `roomote upgrade --skip-backup`

Batch closely related approvals when the exact actions are known. Do not ask for
confirmation for OS inspection, resource checks, downloading the installer to a
temporary file, reading it, DNS lookups, `roomote status`, or redacted health
checks.

The user must personally complete browser sign-in, OAuth consent, provider-app
installation, billing acceptance, and secret entry. Pause at those steps. Do
not capture the browser, setup URL, tokens, or secrets in a transcript.

## Detect before choosing a path

Report, without changing the machine:

- host OS and version, kernel, architecture, and whether execution is inside a
  VM, container, WSL, or bare metal
- CPU count, total memory, free disk, and whether other production workloads
  share the host
- whether Docker Engine and the Compose plugin are installed and healthy
- whether `systemd`, `curl`, and `openssl` are available
- whether TCP ports 80 or 443 are already in use
- default route, public IPv4 detection, DNS control, NAT/CGNAT constraints, and
  firewall ownership

Roomote publishes Linux images for `amd64` and `arm64`. Use at least 4 GB RAM;
prefer 4 vCPU, 8 GB RAM, and 60 GB of quota-capable disk when Docker task
sandboxes share the host. Stop and ask the user to choose a larger or different
host when resources are below that practical baseline, the target is an LXC
container, or unrelated production workloads share the host.

## Choose the supported topology

| Detected environment | Default path | Contract |
| --- | --- | --- |
| Fresh Ubuntu or Debian VPS/server, `amd64` or `arm64` | Install directly | Preferred and fully automated installer path. Use a stable domain for production. |
| Other native Linux | Do not assume automatic support | The installer can continue only when Docker Engine and Compose are already installed and the host provides systemd. Prefer an Ubuntu/Debian VM instead of adapting package-manager or service behavior. |
| macOS | Ubuntu 24.04 VM or a Linux VPS | The installer rejects macOS. For evaluation, create a Multipass VM after approval and run the installer inside it. Use a VPS for production. |
| Windows | Ubuntu 24.04 VM or a Linux VPS | The installer rejects Windows. Multipass is the documented local evaluation topology. Use a VPS for production. |
| WSL2 | Do not use as the default | WSL2 is not a supported installer recommendation because Docker, `systemd`, reboot persistence, and inbound networking vary. Do not claim support based only on a Linux `uname`; use a full Linux VM or VPS. |
| LXC/container | Stop | The default Docker sandbox path depends on networking, cgroups, packet filtering, and writable-layer quotas. Move to a full VM or server. |

### macOS evaluation VM

Docker Desktop is supported for developing Roomote from source, but it is not a
substitute for the Linux server expected by the self-hosting installer. The
supported local installer topology is a Linux guest with its own Docker Engine,
`systemd`, filesystem, and network stack. Do not mount the macOS Docker socket
into the guest.

After approval, the documented evaluation VM is:

```sh
brew install --cask multipass
multipass launch 24.04 --name roomote --cpus 4 --memory 6G --disk 40G
multipass shell roomote
```

Use a stable public HTTPS route to the guest before configuring OAuth or
webhooks. Prefer running `cloudflared` inside the guest so the tunnel reaches
the guest's Caddy directly and does not depend on host-to-guest forwarding.

### Windows evaluation VM

After approval, use a full Ubuntu VM. Multipass is the installer-documented,
PowerShell-friendly option:

```powershell
winget install -e --id Canonical.Multipass
multipass launch 24.04 --name roomote --cpus 4 --memory 6G --disk 40G
multipass shell roomote
```

Docker Desktop's WSL2 backend does not make Windows itself a supported Roomote
installer host. Do not install into WSL2 unless the user explicitly chooses an
unsupported experiment after being told to expect differences in service and
network behavior.

### Native Linux or VPS

Use a fresh Ubuntu or Debian host. The installer runs as root, installs Docker
Engine and Compose when missing, writes the deployment under `/opt/roomote`,
installs `/usr/local/bin/roomote`, and enables the `roomote-compose` systemd
unit. It requires `curl` and `openssl`; automatic Docker installation is only
implemented for Ubuntu and Debian.

The installer publishes only Caddy's TCP ports 80 and 443. PostgreSQL, Redis,
MinIO, the API, preview proxy, and queue dashboard remain on internal Docker
networks. Never expose those services to work around ingress problems.

## Choose public ingress

Choose one final app hostname before browser setup. Roomote derives browser
links, auth redirects, webhooks, artifact URLs, and preview URLs from this
origin. Changing it later requires updating the deployment and every provider
registration.

### Production default: domain, public DNS, and Caddy

Use this path for a VPS or server with public ingress:

1. Ask for the final app domain and confirm the user controls its DNS.
2. For the default flat preview layout, require A records for the app hostname
   and its first-level wildcard, plus matching AAAA records when IPv6 is used.
3. Confirm TCP 80 and 443 are allowed by the cloud/host firewall and not used by
   another service.
4. Run the installer with `--domain` after approval.

```sh
curl -fsSL https://get.roomote.dev -o /tmp/roomote-install.sh
less /tmp/roomote-install.sh
sudo bash /tmp/roomote-install.sh --domain roomote.example.com
```

The default flat preview name is
`<task>-<port>-preview.roomote.example.com`, covered by
`*.roomote.example.com`. A separate `--preview-domain
preview.roomote.example.com` uses `<task>-<port>.preview.roomote.example.com`
and requires both the preview hostname and its wildcard plus certificate
coverage for the nested wildcard. Do not select the dedicated layout unless
the user needs nested previews or dedicated preview-cookie isolation and their
DNS/TLS provider supports it.

Without `--domain`, the installer derives an `sslip.io` hostname from the
server's public IPv4. Treat that as a short evaluation path only: it is tied to
the IP and shares public certificate rate limits.

### Evaluation or homelab: Cloudflare Tunnel

A named Cloudflare Tunnel is appropriate when evaluating from a Linux VM,
operating behind CGNAT, or intentionally keeping inbound router ports closed.
It still requires a stable domain in the user's Cloudflare account. Do not use
an ephemeral Quick Tunnel for OAuth/webhook setup or promise live previews from
one; its hostname is not stable and it does not establish the required wildcard
hostname contract.

After the user approves the external-account and DNS changes:

1. create a named tunnel without asking the user to reveal its token
2. configure the app hostname and the flat wildcard hostname to reach the same
   Caddy instance on HTTPS port 443
3. install Roomote with `--domain <host> --tls-mode internal`
4. configure cloudflared to trust Caddy's local CA, or use `noTLSVerify: true`
   only for the private tunnel-to-Caddy hop
5. enable **Match SNI to Host** for the wildcard hostname

```sh
sudo bash /tmp/roomote-install.sh \
  --domain roomote.example.com \
  --tls-mode internal
```

Cloudflare must present a publicly trusted browser certificate even though the
private origin hop uses Caddy's internal certificate. Route all app, API,
artifact, webhook, and preview traffic through Caddy rather than directly to an
application container.

## Install and resume safely

Download the installer to a temporary file, identify the exact version and
flags, let the user inspect it, and obtain approval before running it as root.
Do not recreate the Compose stack manually.

The installer supports safe reruns. An existing `/opt/roomote/.env` preserves
generated secrets and the existing domain when no replacement is supplied,
while deployment-owned image and URL metadata are refreshed. On a failed or
interrupted install:

1. inspect `sudo roomote status` when the CLI exists
2. inspect only the relevant service with `sudo roomote logs <service>` and
   redact secrets and tokenized URLs
3. correct the prerequisite, DNS, port, or Docker failure
4. rerun the same installer command; do not delete `/opt/roomote/.env` or Docker
   volumes

Ask before changing an existing domain, preview domain, TLS mode, or manual env
override. Never “start clean” by deleting state unless the user explicitly
chooses data loss after a backup.

## Browser setup and generated URLs

When services are healthy, ask the user to run this in a separate trusted
terminal and open the result themselves:

```sh
sudo roomote setup-url
```

Do not run that command in a captured agent terminal, print its output, or
repeat the tokenized URL. The link grants first-admin bootstrap access.

The user can create the first admin with email/password; Slack or Microsoft SSO
can be configured later. The user must then configure source control, inference,
a sandbox provider, optional communications, and the first environment in the
browser.

Provider registrations must use the exact final public origin. Important paths
include:

| Purpose | Public URL |
| --- | --- |
| GitHub setup and callback | `<origin>/github/callback` |
| GitHub webhook | `<origin>/_roomote-api/api/webhooks/github` |
| Slack OAuth callback | `<origin>/api/slack/callback` |
| Slack events and interactivity | `<origin>/_roomote-api/api/webhooks/slack` |
| Slack sign-in redirect | `<origin>/api/auth/oauth2/callback/slack` |
| Microsoft sign-in redirect | `<origin>/api/auth/oauth2/callback/microsoft-entra-id` |
| Microsoft Teams bot endpoint | `<origin>/api/webhooks/teams` |

Use the relevant [source-control](/source-control) and
[communications-provider](/communications) pages for complete permissions and
provider-specific URLs. Discord uses its Gateway service rather than a public
webhook callback.

## Verify before declaring success

For an installer deployment, use `sudo roomote status`; `pnpm run doctor` is a
source-checkout/local-development command and is not the host CLI's production
health check.

Verify in this order:

1. `sudo roomote status` reports the Compose services healthy.
2. Open the public origin from outside the host or home LAN and verify a
   publicly trusted certificate.
3. Confirm sign-in succeeds and the expected repositories appear after source
   control is connected.
4. Validate the configured sandbox provider in **Settings → Sandboxes**.
5. Run a small task that clones a repository and executes a harmless command.
6. Confirm its transcript/logs and a generated artifact are accessible.
7. If the environment declares a preview port, open its generated preview from
   an external network and verify wildcard DNS, TLS, and proxy routing.
8. For each configured communications provider, send one real message and
   confirm Roomote receives and replies to it.
9. Review **Settings → Deployment → Diagnostics** for the running application
   version and schema migration.

`roomote status` and the local development doctor primarily prove local service
health. They do not by themselves prove public DNS, TLS, OAuth redirects,
provider webhook delivery, or wildcard previews; the external checks above are
required.

## Leave a recoverable deployment

Give the operator these commands:

```sh
sudo roomote status
sudo roomote logs [service...]
sudo roomote restart [service...]
sudo roomote up
sudo roomote down
sudo roomote backup
sudo roomote upgrade
sudo roomote rollback
sudo roomote restore /path/to/backup.roomote --yes
```

Create an encrypted backup after setup if the user approves the brief
application-writer pause. Store the `.roomote` bundle off-host and its
12-or-more-character
passphrase separately. Use `--include-redis` only when queued work, schedules,
sessions, and transient Redis state must be preserved. External object storage
requires its own provider-level backup.

`roomote upgrade` creates an encrypted pre-upgrade backup by default and
preserves the previous release as the supported rollback target. Never skip the
backup without explicit approval. `roomote restore ... --yes` overwrites
configuration and data; verify the bundle and obtain a separate destructive
confirmation immediately before running it.

Finish with a concise report containing the topology, stable public origin,
ingress and preview layout, configured provider categories, verification
results, backup location (never its passphrase), and any unsupported choices or
remaining operator action.
